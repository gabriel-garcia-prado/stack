# Conventions for AI agents

Full-stack TypeScript monorepo: Hono API on Bun (`apps/api`) + React/Vite web app (`apps/web`).
The web app gets a fully typed RPC client by importing the API's `AppType` (`@stack/api`).

## Hard rules

- **Bun only, never Node.** Run tools with `bun` / `bunx --bun`. Do not add Node-specific tooling or `engines.node`.
- **Always finish by running `bun run check`** (typecheck + lint + test) from the repo root. It must pass.
- **Errors are neverthrow `Result`s, never thrown.** Business logic returns `Result`/`ResultAsync` with an `AppError`
  (`src/types/errors.ts`); handlers convert it to HTTP via `c.var.appResponse(...)`. Don't `throw` across module
  boundaries and don't add try/catch in handlers.
- **Never wrap `zValidator` in `createMiddleware`** — it erases the validated input types from the route and silently
  breaks the typed RPC client. Use the `validator(target, schema)` helper from `src/middleware/validator.ts` inline in
  the route chain.
- **Register API routes before the static catch-all** in `apps/api/src/index.ts`; `export type AppType` must stay above
  the `serveStatic` handlers or the RPC client loses all route types.
- **Protected endpoints use the `requireAuth` middleware** (`src/middleware/require-auth.ts`), which validates the
  session server-side. Client-side gating in the web app is UX only, never security.

## Imports

Inside `apps/api`, the shared infrastructure that every module exercises has a `#`-prefixed subpath alias declared in
the `imports` field of `apps/api/package.json`: `#factory`, `#errors`, `#environment`, `#database` (also re-exports
the drizzle schema tables), `#validator`, `#require-auth`, `#test`. Use these when building a new module; feature
modules (like auth) and one-off files don't get aliases — import them relatively. Don't add tsconfig `paths` for API
code — package imports are the one mechanism that works across Bun, tsc, and the esbuild-based CLIs, and they don't
leak into the web app. The web app keeps its own `@/*` alias (declared in `apps/web/tsconfig.json` and
`vite.config.ts`).

## API module layout

Each feature lives in `apps/api/src/modules/<name>/`:

- `<name>.ts` — pure business logic; dependencies injected as a plain object, returns `ResultAsync`.
- `<name>.handler.ts` — HTTP wiring: a sub-app created with `factory.createApp()`, mounted in `index.ts` via
  `.route('/api/<name>', <name>Routes)`.
- `<name>.test.ts` — unit tests with mocked dependencies (see `src/lib/test.ts` helpers).

`src/index.test.ts` holds integration tests (via `app.request`) plus compile-time assertions that the RPC client types
stay inferred — extend those when adding routes.

## Environment & database

- Read env only through `src/types/environment.ts` (validated with Zod at startup); add new variables to the schema and
  to `.env.example`.
- Drizzle schema lives in `apps/api/drizzle/schema/`; column names derive from `casing: 'snake_case'` — don't pass
  explicit column name strings. After schema changes run `bun db:generate` (and `bun db:migrate` locally).
- `drizzle/schema/auth.ts` is generated by `bun auth:generate` — don't edit it by hand.
- Dev seeding lives in `drizzle/utils/seed.ts` (runs in `bun dev`, never in production). It creates the dev login
  `dev@example.com` / `password1234` through Better Auth's API — add new seed data there and keep it idempotent.
